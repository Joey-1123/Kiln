# Reference Analysis: Soup · colibri · FreeToken

Reverse-engineered specifications of the three cloned reference repos (`references/`), produced with the spec-miner workflow (grounded in actual files read) and architecture-designer framing (patterns, trade-offs, decisions worth reusing).

## 1. What each project is

| | **Soup** | **colibri** | **FreeToken** |
|---|---|---|---|
| One-liner | CLI that fine-tunes / post-trains LLMs in one command (QLoRA, DPO/GRPO/KTO…) | Pure-C inference engine running 744B–2.8T MoE models via VRAM/RAM/NVMe multitiering | Edge-native MoE *serving* engine; bandwidth-adaptive CPU-GPU co-execution |
| Language | Python 3.10–3.12 (Typer + Pydantic v2) | C99 (single `.c` per model family) + stdlib-only Python control plane + React/Tauri UI | Python ≥3.10 + torch 2.11 + Triton + 2 AOT C++ extensions |
| Core trick | Layer streaming: frozen base streams into VRAM one decoder layer at a time → 8B on 4 GB GPU, bit-exact | "A JIT for weights": routing heat drives LRU/pinned/VRAM/disk placement; placement changes speed only, never semantics | Global device-side LRU expert cache + q\* bandwidth-matched CPU/GPU fetch split; CUDA-graph-capturable decode |
| Config surface | `soup.yaml` → Pydantic v2 schema (single source of truth), ~24 tasks | Env vars parsed in one `main()` block; docs generated by scanning `getenv()` sites; `COLI_POLICY` presets | CLI flags + auto-resolution from checkpoint+GPU; measured self-calibration artifacts (`ft bench bw`) |
| Serving/API | OpenAI-compatible `soup serve`; MCP server | OpenAI-compatible gateway (`openai_server.py`, sentinel-framed stdio protocol to engine) | FastAPI frontend ⇄ ZMQ ⇄ tokenizer ⇄ scheduler (3-process topology); OpenAI + Anthropic + Responses APIs |
| License | Apache-2.0 | Apache-2.0 | Apache-2.0 |

Common mission across all three: **frontier-scale models on consumer hardware**, treating RAM/VRAM/storage as one memory hierarchy, with correctness ("never silently change model semantics") as a hard invariant and measurement culture everywhere (benchmarks published including failures).

## 2. Soup — key findings

### Stack
- Hatchling src-layout, entry `soup = soup_cli.cli:run`, Typer CLI (~100 command modules, ~230 documented invocations).
- Light core install (no torch); all training deps in `[train]` extra; 25+ extras (`fast`/unsloth, `mlx`, `serve`, `eval`, `mcp`…).
- Pydantic v2 config schema `src/soup_cli/config/schema.py` = **6,905 lines, single source of truth**; root `SoupConfig` with `task` Literal of 24 tasks.

### Architecture highlights (worth copying)
1. **Light-core / lazy heavy imports enforced by runtime probe test** — `tests/test_cli_startup_is_light.py` imports the CLI in a fresh interpreter and asserts torch never lands in `sys.modules`. "A lazy import that is CALLED at module scope is not lazy."
2. **Drift-proof constants** — schema imports numeric bounds from the modules enforcing them at runtime, so schema and runtime validator can never disagree.
3. **Cross-field legality gates** — `model_validator(mode="after")` rejecting invalid feature combos with precise messages.
4. **Path containment** — `utils/paths.py`: `realpath` + `commonpath` (NOT `resolve()+relative_to()`, breaks on Windows 8.3 names), symlink/junction rejection, atomic `mkstemp`+`os.replace`.
5. **Planner/runtime split** — `layer_stream.py` is deliberately torch-free so lightweight commands can forecast runs; architecture allowlist (fail loud, not silently mis-train).
6. **MCP server SDK isolation** — pure handler table in `registry.py`; only `server.py` imports `mcp`; stdout protected for JSON-RPC; execution gated behind single-use confirmation tokens.
7. **Friendly error mapping** — raw exception substrings → short message + exact fix command incl. correct pip extra; semantic exit codes as API (ship: 0/1/2/3).
8. **CI tests process, not just behavior** — dependency-contract jobs, version sync tests, changelog fragment tests; UTF-8 bootstrap before any console exists (Windows cp1252 safety).
9. **AGENTS.md as first-class contributor onboarding** for AI coding agents.

## 3. colibri — key findings

### Stack
- Engines: `colibri.c` 11,282 LOC (GLM-5.2 reference), `deepseek_v4.c` 17,017, plus kimi_k3/qwen36/inkling/olmoe — one binary per family.
- Shared mechanisms live in `#ifndef`-guarded headers of static functions: `st.h` (safetensors index, pread-only, mirror replicas), `quant.h` (all SIMD kernels), `tier.h` (LFRU placement math), `expert_store.h` (ops-struct plugin seam), `route_trace.h`, `kv_prefix.h`, `decode_batch.h`.
- GPU: CUDA/Metal/Vulkan backends loaded at runtime through opaque-handle ABI loaders with graceful CPU fallback; MinGW host + MSVC/nvcc DLL boundary hygiene.
- Python control plane is stdlib-only (`coli` launcher 2,019 LOC, `openai_server.py` 3,619 LOC, `resource_plan.py` planner). Web UI React18+TS; desktop Tauri v2 wrapping same bundle.

### Per-token pipeline
route → batch-union expert resolution (pinned ∪ VRAM ∪ LRU ∪ disk, one coalesced pread per expert into slab views) → PILOT router-lookahead prefetch via lock-free SPMC ring (71.6% predictable one layer ahead) → int4 grouped GEMMs → MLA compressed KV (576 vs 32k floats/token) → MTP speculation verified batched → telemetry + `.coli_usage` learning cache + REPIN rebalancing.

### Highlights (worth copying)
1. **Header-shared mechanism libraries + single-TU engines** — a fix reaches all model families at once; recurring defects historically came from mechanisms landing in one engine only.
2. **Semantics-preserving degradation invariant** — insufficient fast memory may reduce speed; must never quietly redefine the model. Every optimization is value-neutral or explicitly opt-in + measured.
3. **Ops-struct plugin seam** for expert stores with written lease contract (release exactly once, prefetch advisory, no evict-under-lease).
4. **Sentinel-framed stdio protocol** between gateway and engine (`\x01\x01READY`, length-prefixed `\x02PROMPT`, unknown extension keys reject frame) with `O_BINARY` enforcement on Windows.
5. **Correctness anchored to a transformers oracle in CI without torch/network** — tiny deterministic numpy fixtures + committed oracle logits; teacher-forced position-by-position compare.
6. **Generated env-var documentation** — `ENVIRONMENT.md` regenerated by scanning every `getenv()` site; quarantined experiments require explicit opt-in and print measured failure data.
7. **Dual-SSD striping validated at startup** (byte-identical shard check), partial mirrors fine, mirror never written, read errors degrade not crash.
8. **Format inference from byte/scale arithmetic** instead of on-disk ordinals + documented private ordinal block governance.

## 4. FreeToken — key findings

### Stack
- torch 2.11 pinned `<2.12`, Triton always-on kernel layer, flashinfer/sglang-kernel optional (`[accel]`); two AOT C++ exts (`_pinned_tensor`, `_cpu_moe` with AVX512-BF16 dispatch).
- 3-process topology: uvicorn frontend ⇄ ZMQ typed-dataclass messages ⇄ tokenizer worker ⇄ scheduler (owns Engine + CUDA device). Overlap scheduling on second CUDA stream.

### Core machinery
- **Banks**: pinned host RAM tensors per expert-layer, layouts declared once in `_BANK_SCHEMAS` per quant format (bf16/fp8_block/q4_0/nvfp4/mxfp4/ds_fp4) — cache machinery stays format-agnostic.
- **Decode**: device-side LRU `ensure_experts` rewrites `topk_ids`→slot ids in place (= the ABI), fixed-shape ⇒ CUDA-graph capturable; misses stream H2D in coalesced runs.
- **Prefill**: double-buffered whole-layer streaming ring; optional hit-D2D gather (gated on CUDA≥13 due to a bisected driver bug documented inline).
- **q\*** policy: `ft bench bw` measures CPU-GEMV vs PCIe bandwidth; fetch fraction computed as `pcie_ov/(pcie_ov+cpu_ov)` in Q16 fixed point so Triton kernel and Python agree exactly; overflow ids rewritten −1 → CPU executor.
- **Semantic anchors**: GDN recurrent state snapshotted at first tool-call opener token, donated (not copied) to radix tree — agentic context edits resume from anchor.
- **Elastic VRAM**: `cache_budget.py` pure integer math (MoE-first split); runtime `POST /v1/cache/rebuild` re-partitions pools without restart.
- **FTW format**: single contiguous byte region sliced into ≤8GiB shards, everything 4096-aligned for O_DIRECT `preadv`; stores pre-repacked expert banks.

### Highlights (worth copying)
1. Declarative capability matrices (`BackendInfo`) for attention backend selection — registration never imports kernels.
2. Pure-function policy modules (budget math, cost models) isolated from side effects — unit-testable without CUDA.
3. Single-source bank schema registry deriving kernels/dispatch/validation.
4. Measured self-calibration shipped as cached artifact keyed by (GPU UUID, format), stale-hardware detection.
5. Torch-free supervisor daemon (`ft daemon`) so a CUDA segfault can't kill control plane — enforced by import-sentinel test.
6. Prebuilt JIT kernel-cache wheel keyed by specialization signature; `FREETOKEN_DISABLE_JIT=1` hard-fails release validation.
7. `ft launch` scrubs cloud API keys from child env so coding agents can't silently fall back to paid endpoints.
8. Test-placement philosophy: only test logic that can fail *silently*, asserted against independent references.

## 5. Cross-cutting patterns (the shared DNA)

These recur in all three and should be treated as requirements for our project:

1. **Correctness is non-negotiable; speed is negotiable.** Placement/caching/streaming may change tok/s, never tokens. Validated against independent oracles (transformers teacher-forcing in colibri; bit-exact streamed-vs-resident asserts in Soup; dequant/CPU-mirror oracles in FreeToken).
2. **Measurement culture.** Benchmarks published as-written including failures/retractions; comments cite host + numbers + issue IDs; knobs default from measurements; experiments are hypotheses until end-to-end A/B.
3. **Light/torch-free control plane around heavy compute.** Lazy heavy imports probed at runtime (Soup), stdlib-only gateway (colibri), torch-free daemon (FreeToken). Heavy deps never load on the fast path of tooling.
4. **Single source of truth for configuration**, with drift-proof bounds and generated documentation (Pydantic schema / getenv scan / checkpoint-derived auto-config).
5. **Fail-open instrumentation, fail-closed security.** Audit/telemetry best-effort; path containment, confirmation-gated execution, env-key scrubbing strict.
6. **Plugin seams via small ops structs / capability tables** rather than inheritance: expert stores (colibri), attention backends (FreeToken), trainer task wrappers (Soup).
7. **Semantic exit codes, friendly error mapping, doctor/plan/tune triads** for operability (`soup doctor`, `coli plan/doctor/tune`, `ft ctl/checkpoint/bench bw`).
8. **Windows is a first-class target** in all three (UTF-8 bootstrap, O_BINARY, junction handling, MinGW↔MSVC ABI bridges) — relevant to our dev environment.
9. **AGENTS.md / repo conventions for AI agents** (Soup formalizes it; all three carry measured-evidence comment style).

## 6. Complementary positioning

- **Soup** = training/post-training layer (writes adapters), Python-first, config-driven UX excellence.
- **colibri** = extreme low-footprint inference (CPU/disk-bound tiering), C, zero deps, correctness-oracle CI.
- **FreeToken** = GPU-forward serving with graph-capturable offload, production API surface (OpenAI/Anthropic/Responses), agent-launcher ergonomics.

Together they span train → serve → operate on consumer hardware. A new project in this space would plausibly combine: Soup's config/CLI/governance patterns, colibri's tiering/oracle-validation discipline, and FreeToken's process topology + capability matrices + elastic memory management.

## 7. Open questions before we design our project

1. What is our primary goal: training, inference/serving, or an integrated train→serve loop?
2. Target language split (Python-only like FreeToken/Soup, or native core like colibri)?
3. Which model families/architectures are first-class (MoE? hybrid GDN/SSM? dense)?
4. Minimum hardware floor (laptop-class like colibri's 25 GB origin, or gaming-GPU like FreeToken)?
5. Do we need the compliance/governance surface (BOM, attestations, audit logs — Soup-style) from day one?
